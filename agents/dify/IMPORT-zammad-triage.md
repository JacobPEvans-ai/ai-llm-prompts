## Import and schedule

Target: Dify 1.16.1 or 1.18.0 with Workflow apps, Schedule Trigger support, and App DSL 0.7.0.

## Generated DSL source and synchronization

The workflow DSL is generated by `agents/dify-src/render.py` from `agents/zammad-triage.yaml`, its workflow templates,
and the prompt sources declared by the YAML. Edit the YAML or canonical prompt source and run
`python3 agents/dify-src/render.py`; for graph changes, edit the template under `agents/dify-src/zammad-triage/` too.
Commit all changed sources with the generated DSL. The CI check fails on any byte difference. Never copy or paste a
prompt by hand.

1. Configure the OpenAI-compatible provider and the `litellm_role` declared in `agents/zammad-triage.yaml` (`medium`).
   Its router key must be scoped to local-only models; cloud fallback is forbidden.
2. Import [zammad-triage.dsl.yml](./zammad-triage.dsl.yml) as a **Workflow** app, not a Chatflow. The agent's router
   key is `openbao://agent-key/zammad-triage` from `agents/zammad-triage.yaml`.
   Dify sets model-provider credentials per workspace. This app uses the workspace key from step 1 unless the per-agent design question changes it.
3. Set the native Schedule Trigger from `trigger.cron` in `agents/zammad-triage.yaml` (`*/10 * * * *`, ten minutes,
   minute resolution). Scheduled inputs are {}; the workflow uses sys.timestamp. Publish with ZAMMAD_TRIAGE_MODE=shadow.

## Protected environment values

Resolve policy refs to JSON arrays of opaque group ID strings. Keep values in protected Dify settings. Include all client
and business group IDs in the denied array; the guard rejects tickets outside its computed scope even if search returns
them.

| Policy ref | Dify environment variable |
| --- | --- |
| policy://zammad-triage/allowed-groups | ZAMMAD_TRIAGE_ALLOWED_GROUPS |
| policy://zammad-triage/readonly-groups | ZAMMAD_TRIAGE_READONLY_GROUPS |
| policy://zammad-triage/denied-groups | ZAMMAD_TRIAGE_DENIED_GROUPS |

Also configure ZAMMAD_TRIAGE_TAG_VOCABULARY as a JSON array, ZAMMAD_TRIAGE_MODE (shadow by default), OPENBAO_ADDR,
OPENBAO_ROLE_ID, OPENBAO_SECRET_ID, ZAMMAD_TOKEN_PATH, and ZAMMAD_API_BASE with approved values. Leave the API base
empty until provisioned. The AppRole is agent-zammad-triage; the token path resolves the Zammad API token. The request
header is Authorization: Token token= followed by the fetched token. The token stays inside the two code nodes that
call Zammad and is never a workflow variable, log line, or output.

The search node refuses malformed group policy and an empty read scope. It searches each group in
allowed ∪ readonly, subtracting denied IDs. Deny wins, and readonly groups permit reads only. Malformed policy denies
all reads and writes. Every HTTP request rejects redirects.

## Enable Langfuse tracing

Do this before the first published run.

1. In the Dify console, open this app, select **Monitoring**, then **Tracing app performance**, then
   **configure**. Dify documents this at
   <https://docs.dify.ai/en/use-dify/monitor/integrations/integrate-langfuse>.
2. Enter the Public Key, Secret Key, and Host of the shared Langfuse project. Keep the values out of this
   file and out of Git. Read the two keys from the OpenBao KV v2 leaf named by the variable
   `DIFY_LANGFUSE_OPENBAO_PATH` in mount `secret`, fields `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY`.
   Read the Host from the variable `DIFY_LANGFUSE_HOST`. Both variables come from the runtime secret store.
3. Save. The status on the same page must read started.
4. Acceptance check, after one test run of the published app: take the top-level `workflow_run_id` from the
   blocking response of that run's Workflow Run API call, documented at
   <https://docs.dify.ai/en/api-reference/workflow-runs/run-workflow>. A Langfuse trace with that id must exist
   (inferred from Dify's Langfuse field table, which maps `workflow_app_log_id/workflow_run_id` to the `id`
   column; confirm at first import, and if the trace id differs, match on the run id in trace metadata instead).
   The router log line for this run's request shows the key alias that request used. Take the alias from that
   line. If the alias is not the one this app uses, stop before any promotion.

## Shadow trace and promotion

Check the Langfuse trace for the scheduled Workflow run. Confirm its output contains the intended action JSON,
mode: shadow, and an empty results array, and that no Zammad write request ran. Verify the model received only ticket index,
title, priority, state name, age, tags, and last-updated age, with no customer fields or article bodies.

Live writes are hard-disabled in the guard (`LIVE=False`), so ZAMMAD_TRIAGE_MODE=live still yields shadow output. A
ticket title can steer the model, so the guard does not trust a proposal just because its shape is valid. Enable live
writes only in a reviewed change, after an executable injection eval runs in the DSL tests and proves that injected
proposals are rejected. Live mode would then dispatch only guarded priority updates, vocabulary tags, and fixed
internal notes. It stops at the first failed write and denies the rest of the plan. Incident proposals remain output
only, and a note may never carry the incident_candidate reason.
